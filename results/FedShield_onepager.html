How it works

  • Features (RBIH MuleHunter families): 1h–7d activity peaks, channel bursts (UPI/IMPS/NEFT/ATM), pass-through, bidirectional counterparties, concurrency, amount-digit patterns, MCC outliers. 398M transactions processed out-of-core with DuckDB.
  • Federated GBDT on histograms. Lossless against pooled training. Pairwise-masked secure aggregation.
  • Byzantine gates: a peer AUC-PR probe at the start and a per-tree gradient-direction consensus check.
  • Hashed suspect registry: rare counterparties and devices shared with confirmed mules at other banks, as HMAC digests only.
  • Label shield: 1,907 doubtful labels down-weighted (flag outside the data window, "Routine Investigation", no reason, flag before any activity).
  • Graduated response (monitor → cooling-off → limit → lien → freeze) with an audit trail feeding labels back.

Prototype

  • 5 roles, server-enforced scope: Bank A/B/C officers, aggregator, RBI. A bank asking for another bank's account gets 403 live.
  • Live pipeline: watch masked packets, gate decisions, privacy ledger and learning curve as the model trains.
  • RBI view: pseudonymised cross-bank clusters, evidence provenance, pattern library, audit trail.
  • Portable: one adapter contract. NFPC, IBM AMLworld and BAF all run on the same core.
  • Stack: FastAPI, React/TS, Cytoscape, DuckDB, numba, Redis, Redpanda, Docker Compose (one container per bank).
  • Reproducible: Kaggle notebooks call the same modules.
Limits: banks are simulated partitions of one dataset. EFRM/AML/I4C evidence feeds are simulated. Formal DP is costly at this scale (ε 16–64 → AUPRC ≈ 0.2 on the small sweep model). Explanations are tree-path attributions.
